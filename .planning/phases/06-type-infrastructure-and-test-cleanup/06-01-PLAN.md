Create `src/types/project.ts` with a minimal TypeScript interface for Project data from external CMS API.

**Interface structure:**
- `id: string` — Unique identifier from CMS
- `title: string` — Project name/title
- `description: string` — Brief description (1-2 sentences)
- `content?: string` — Detailed case study content (problem, solution, outcome) — optional
- `techStack: string[]` — Array of technologies/frameworks used
- `links?: { demo?: string; github?: string; live?: string; }` — Optional project links object
- `image?: string` — Featured image/screenshot URL — optional
- `publishedAt?: string` — Publication/completion date — optional

**Implementation guidelines:**
- Use `interface` (not `type` alias) per TypeScript conventions for object shapes
- Mark fields optional (`?`) when they may not be present in all CMS responses
- Include JSDoc comments documenting this is a placeholder to be refined in Phase 8
- Note in comments: "No runtime validation — CMS API handles data validation"
- Use `string[]` for techStack (not union types) — CMS determines valid values

- Do NOT add Zod schemas or runtime validation (user explicitly deferred to Phase 8)
- Do NOT add type guards like `isProject()` functions (not needed until CMS integration)
- Do NOT add default values or factory functions (CMS provides data)
- Do NOT over-design with complex nested types (keep minimal — this gets swapped out in Phase 8)

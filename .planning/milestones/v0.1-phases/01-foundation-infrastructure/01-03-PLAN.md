
    2. Verify exclusions:
       - `node_modules`: Will be installed fresh in container (prevents bloat)
       - `dist`: Will be generated during build (not copied from host)
       - `.git`: Not needed in container (saves space)
       - `.env*`: Security - never include secrets in image
       - `.planning`, `.opencode`, `design-system`, `.github`: Project artifacts not needed at runtime
    
    3. What IS included (not in .dockerignore):
       - `package.json` and `package-lock.json` (needed for npm install)
       - `src/` directory (source code to build)
       - `public/` directory (static assets)
       - `astro.config.mjs` (Astro configuration)
       - `tsconfig.json` (TypeScript configuration)
    
    **Why this matters (per research Pitfall 1):**
    - Including `node_modules`: Bloats image to 400MB+
    - Excluding `src/` or `public/`: Build fails with missing files
    - Including `.git`: Adds 50-100MB+ of useless history
    
    **Don't:**
    - Don't exclude `package.json` or `package-lock.json` (build will fail)
    - Don't exclude `src/` or `public/` (no source code to build)
    - Don't include `node_modules` or `dist` from host (inconsistent with container environment)
  </action>

<task type="auto">
  <name>Task 2: Create nginx.conf for static site serving</name>
  <files>nginx.conf</files>
  <action>
    Create `nginx.conf` with proper configuration for serving Astro static site:
    
    1. Create `nginx.conf` at project root with this content:
       ```nginx
       worker_processes  1;
       
       events {
         worker_connections  1024;
       }
       
       http {
         server {
           listen 80;
           server_name   _;
           
           root   /usr/share/nginx/html;
           index  index.html index.htm;
           include /etc/nginx/mime.types;
           
           gzip on;
           gzip_min_length 1000;
           gzip_proxied expired no-cache no-store private auth;
           gzip_types text/plain text/css application/json application/javascript application/x-javascript text/xml application/xml application/xml+rss text/javascript;
           
           error_page 404 /404.html;
           location = /404.html {
             root /usr/share/nginx/html;
             internal;
           }
           
           # CRITICAL: Handles direct navigation to /about, etc.
           # Without this, refreshing /about returns 404
           location / {
             try_files $uri $uri/index.html =404;
           }
         }
       }
       ```
    
    2. Verify critical directive present:
       - `try_files $uri $uri/index.html =404;` (per research: Pitfall 2)
       - This tells Nginx: try exact URI first, then try URI/index.html, then 404
       - Without this: direct navigation to /about fails (works in dev, breaks in production)
    
    3. Additional features:
       - Gzip compression for text assets (faster page loads)
       - MIME types included (proper Content-Type headers)
       - Custom 404 page support (will use Astro-generated 404.html)
    
    **Why try_files matters (per research Pitfall 2):**
    - Astro builds `/about` as `/about/index.html`
    - Without try_files: Nginx looks for literal `/about` file, returns 404
    - With try_files: Nginx tries `/about`, then `/about/index.html`, finds it
    - Symptom without this: internal nav works, direct URL navigation breaks
    
    **Don't:**
    - Don't omit `try_files` directive (most common pitfall)
    - Don't use `try_files $uri $uri/ =404` (missing /index.html fallback)
    - Don't forget `include /etc/nginx/mime.types` (CSS/JS served as text/plain)
  </action>
  <verify>
    <automated>test -f nginx.conf && grep -q "try_files" nginx.conf && grep -q "index.html" nginx.conf</automated>
  </verify>
  <done>
    - `nginx.conf` file exists at project root
    - Contains `try_files $uri $uri/index.html =404;` directive
    - Includes gzip compression configuration
    - Includes MIME types
    - Listens on port 80
    - Root set to `/usr/share/nginx/html`
  </done>

<task type="auto">
  <name>Task 3: Create multi-stage Dockerfile</name>
  <files>Dockerfile</files>
  <action>
    Create multi-stage `Dockerfile` following official Astro Docker recipe:
    
    1. Create `Dockerfile` at project root with this content:
       ```dockerfile
       # Stage 1: Base - common foundation
       FROM node:lts AS base
       WORKDIR /app
       COPY package.json package-lock.json ./
       
       # Stage 2: Production dependencies only
       FROM base AS prod-deps
       RUN npm install --omit=dev
       
       # Stage 3: All dependencies (including dev)
       FROM base AS build-deps
       RUN npm install
       
       # Stage 4: Build the site
       FROM build-deps AS build
       COPY . .
       RUN npm run build
       
       # Stage 5: Runtime - Nginx with built assets only
       FROM nginx:alpine AS runtime
       
       # Copy nginx configuration
       COPY nginx.conf /etc/nginx/nginx.conf
       
       # Copy built static files from build stage
       COPY --from=build /app/dist /usr/share/nginx/html/
       
       # Security: Run as non-root user (INFR-04)
       # nginx:alpine includes nginx user by default
       USER nginx
       
       # Health check (INFR-06)
       HEALTHCHECK --interval=30s --timeout=3s --start-period=5s \
         CMD wget --no-verbose --tries=1 --spider http://localhost/ || exit 1
       
       # Expose port 80
       EXPOSE 80
       
       # Start nginx (must run in foreground for Docker)
       CMD ["nginx", "-g", "daemon off;"]
       ```
    
    2. Verify multi-stage structure (per research Pattern 2):
       - **base**: Common foundation with package.json
       - **prod-deps**: Production dependencies only
       - **build-deps**: All dependencies including dev tools
       - **build**: Actual build process
       - **runtime**: Final image with only static files + nginx
    
    3. Key security/quality features:
       - `USER nginx`: Runs as non-root (per research Pitfall 6, INFR-04)
       - `HEALTHCHECK`: Container health monitoring (INFR-06)
       - `nginx:alpine`: Minimal base image (~10MB vs 130MB for nginx:latest)
       - `node:lts`: Uses Node 22+ required by Astro 6
    
    4. Build process explained:
       - Build stages include TypeScript, dev dependencies → ~400MB
       - Runtime stage only includes `/app/dist` static files → ~50-80MB
       - Multi-stage build discards build artifacts, only keeps runtime needs
    
    **Why multi-stage (per research):**
    - Single-stage: 400MB+ (includes node, TypeScript, dev deps in final image)
    - Multi-stage: <100MB (only nginx + static files in final image)
    - Security: Build-time dependencies never reach production image
    
    **Don't:**
    - Don't use single-stage build (bloated images)
    - Don't run as root (omit USER directive)
    - Don't use `node:lts` for runtime (use nginx:alpine instead)
    - Don't copy `node_modules` explicitly (breaks with .dockerignore)
  </action>
  <verify>
    <automated>test -f Dockerfile && grep -q "FROM.*AS base" Dockerfile && grep -q "FROM nginx:alpine AS runtime" Dockerfile && grep -q "USER nginx" Dockerfile && grep -q "HEALTHCHECK" Dockerfile</automated>
  </verify>
  <done>

    - Includes `HEALTHCHECK` directive

    - Copies `/app/dist` from build stage to nginx html directory
